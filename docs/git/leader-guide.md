# Git の使い方(リーダー向け)

チームのリーダーがこのファイルだけを読んで、準備・日常のトラブル対応・テンプレートの更新・作成者への相談ができるように書いてあります。Git に詳しくなくても進められるように書いています。メンバー向けの使い方は [member-guide.md](member-guide.md) です。先に読んでおくと、メンバーから聞かれたときに答えやすくなります。

## 1. 準備

最初に 1 回だけ行います。

1. **テンプレートからリポジトリを作る。** テンプレートの GitHub ページ(https://github.com/aozora232u/git-simple-template)を開き、緑の **Use this template** →「Create a new repository」を選ぶ。Owner は自分かチームのアカウント、名前は好きなものでよい。**Private**(非公開)でよい
2. **「マージ後にブランチを自動で消す」設定を ON にする(必須)。** 作ったリポジトリの **Settings → General** を開き、少し下にある **Automatically delete head branches** にチェックを入れる(自動で保存される)
   - **理由:** テンプレートからリポジトリを作っても、この設定は引き継がれず、初期は OFF です。スクリプトは「GitHub からブランチが消えた = 提出したものがマージ済み」と判断しています。OFF のままだと、マージした後も同じブランチで「提出」を実行したときに「提出済みの PR に反映されています」と出るのに、実際は main に入りません。成功したように見えて何も届かないので、必ず ON にしてください
3. **メンバーを招待する。** **Settings → Collaborators → Add people** で、メンバーの GitHub のユーザー名かメールアドレスを入れる(メンバー全員に、招待メールの **Accept invitation** を押してもらう)
4. **`README.md` を書き換える内容を決める。** 先頭の `{{プロジェクト名}}` を自分たちのプロジェクト名にし、「## このプロジェクトについて」に説明を書く。冒頭の「Git の使い方は member-guide.md を見てください」というリンクは残す。書き換えを GitHub に届ける方法は手順 6 に書いてある
5. **必要なら `.gitignore` に使う言語の項目を足す。** 末尾の「技術構成が決まったら、言語やフレームワーク用の項目をここに追記する」のところに足す(これも手順 6 で届ける)
6. **自分の PC で 4 メニューが動くことを確かめる。手順 4・5 の書き換えも、ここで GitHub に届ける。** 新しいリポジトリには Issue が 1 つもないので、先に GitHub で Issue を 1 つ作る(リポジトリの **Issues → New issue**。題名は「README を書く」などでよい)。次に、リポジトリをクローンして VS Code で開き、メンバー向けガイドの手順どおりに「作業開始」(今作った Issue の番号を入れる)→ `README.md`(必要なら `.gitignore` も)を編集 → PR.md を書いて「提出」→ 提出ページで **Create pull request** → マージ、まで一度通す。マージしたあと、GitHub 上でそのブランチが自動で消えることも確かめる(消えなければ手順 2 をやり直す)
7. **メンバーにクローン用の URL を伝える。** リポジトリのページの緑の **Code** ボタンに出る `https://github.com/...git` の URL です

## 2. よくあるエラーと直し方

### ログの見方

メンバーが「相談」するとき、`local/logs/` のログファイルを見せてもらってください。1 回の実行(メニューを 1 回選ぶごと)につき 1 ファイルできます。ファイル名は `2026-10-21_123456_start.log` のように「日付_時刻_メニュー名」です(メニュー名は `start`=作業開始、`switch`=ブランチ切り替え、`submit`=提出、`reset`=やり直し)。新しい 50 件だけ残り、古いものは自動で消えます。ログは各自の PC にだけあり、GitHub には送られません。

ログはメモ帳で開けます。見る場所は次の 4 つです。

- **`結果:` の行(読むなら最初にここ)。** `結果: 成功`、`結果: stop`(メンバー自身で直せる失敗)、`結果: die`(環境の失敗。チームのリーダーへ相談)、`結果: 終了コード N`(想定外の終わり方)のどれか。`stop` と `die` では、その次の行に画面に出た文章が入る
- **`$ git ...` で始まる行。** スクリプトが実行した Git のコマンドを、1 つずつ記録している。その下に、出力が `[stdout]`(普通の出力)・`[stderr]`(エラーや警告)として入り、最後に `[終了コード] 0` のように入る。**原因は、`結果: stop` / `結果: die` の行の直前にある、`[終了コード]` が 0 以外のコマンド**。その `[stderr]` に Git が実際に言ったエラーの文章が出ている。途中に 0 以外のコマンドがあっても、正常なことがある(たとえば「提出」では、PR.md を書いてあると `git diff --quiet` が毎回 1 を返す。「差がある = 書いてある」という意味で、失敗ではない)
- **`---- 開始時 ----` のブロック。** 実行を始めたときのブランチ、HEAD(いちばん新しい記録)、`git status --porcelain`(変更中のファイル)、Git のバージョン。「いま何をしていた状態から始まったか」が分かる
- **`---- 終了時 ----` のブロック。** `stop` / `die` で終わったときだけ入る、終わったときのブランチと変更中のファイル。開始時と見比べると、途中で何が変わったか(変わっていないか)が分かる

ログにはほかに、メニュー名・日時、実行中に画面へ出した文章(`画面:` で始まる行)も入っています。

### メッセージごとの原因と直し方

画面の文章がそのまま表の左の列にあります(〈 〉の部分はその場の名前や数字が入ります)。先頭の【stop】【die】は分類の印で、画面には出ません。**stop** はメンバー自身で直せるもの、**die** は環境側の失敗で、画面に「チームのリーダーに相談してください。そのとき、このログファイルを見せてください: ...」と続くものです。

| 表示される文章 | 原因 | 直し方 | ログで見るところ |
|---|---|---|---|
| 【stop】最初に 1 回だけ、名前とメールの設定が必要です。VS Code のターミナルで次の 2 行を打ってから、もう一度実行してください。(2 行の `git config` が続く) | その PC の Git に名前とメールが未設定 | 表示された 2 行をターミナルで実行する。メールは GitHub の Settings → Emails にある `...@users.noreply.github.com` を使う | `$ git config user.name` と `$ git config user.email` が `[終了コード] 1`(出力が空 = 未設定)のあとに `結果: stop` |
| 【stop】ファイルを別の場所に移すか、.gitignore に追加してから、もう一度実行してください。分からなければチームのリーダーに相談してください。(直前に「次のファイルは秘密情報の可能性があるため記録しません:」とファイル名が出る) | `.env`、`*.pem`、`*.key` など秘密情報らしき名前のファイルがある | 表示されたファイルを作業場所の外へ移すか、`.gitignore` に名前を足す。`.env` や `*.pem`、`*.key` は初めから `.gitignore` に入っているので、普通は出ない。出たときは、`.gitignore` を書き換えて外してしまっていないか確かめる | `---- 開始時 ----` の `git status --porcelain` に出ているファイル名 |
| 【stop】Issue の番号は数字で入力してください(例: 12)。 | 「作業開始」で数字以外を入れた | 数字だけを入れて、もう一度実行する | `引数:` の行に入れた文字が出る |
| 【stop】main からは提出できません。先に「作業開始」で自分のブランチを作ってください。 | main にいる状態で「提出」を選んだ | 「作業開始」を先に実行する | `開始時` の `ブランチ: main` |
| 【stop】PR.md に説明を書いてから「提出」を実行してください。 | PR.md がテンプレートのまま | PR.md を書いてから、もう一度「提出」 | `$ git diff --quiet origin/main -- PR.md` の `[終了コード] 0`(差がない = 未記入) |
| 【stop】切り替えられるブランチがまだありません。 | 作業ブランチが GitHub に 1 つもない | 先にだれかが「作業開始」を実行して作業を送る | `$ git for-each-ref ...` の出力が空(`[stdout]` が無い) |
| 【stop】切り替えられませんでした。変更したファイルが切り替え先の内容とぶつかっています。「やり直し(main に戻る)」を実行してから(変更は控えに残ります)、もう一度実行してください。分からなければチームのリーダーに相談してください。 | 手元の変更が、切り替え先のブランチの内容とぶつかる | 「やり直し(main に戻る)」を実行してから、もう一度切り替える | `$ git switch ...` の `[stderr]`(ぶつかるファイル名が出る) |
| 【stop】ブランチ 〈ブランチ名〉 に切り替えられませんでした。変更したファイルが切り替え先の内容とぶつかっています。「やり直し(main に戻る)」を実行してから(変更は控えに残ります)、もう一度実行してください。分からなければチームのリーダーに相談してください。 | 「作業開始」で既存のブランチに戻ろうとして、手元の変更とぶつかった | 「やり直し(main に戻る)」を実行してから、もう一度「作業開始」 | `$ git switch ...` の `[stderr]` |
| 【stop】main に切り替えられませんでした。変更したファイルが main の内容とぶつかっています。「やり直し(main に戻る)」を実行してください(変更は控えに残ります)。分からなければチームのリーダーに相談してください。 | 手元の変更が main の内容とぶつかる | 「やり直し(main に戻る)」を実行する | `$ git switch -q main` の `[stderr]` |
| 【stop】main を最新にできませんでした。「やり直し(main に戻る)」を実行してください(変更は控えに残ります)。分からなければチームのリーダーに相談してください。 | 手元の main に、GitHub の main と食い違う記録がある、または手元の変更が邪魔をしている | 「やり直し(main に戻る)」を実行する。それでも出るときは `$ git pull ...` の `[stderr]` を見て、作成者に相談する | `$ git pull -q --ff-only origin main` の `[stderr]` |
| 【stop】このブランチ(〈ブランチ名〉)は提出とマージが終わり、GitHub から削除されています。「やり直し(main に戻る)」を実行すると、今の変更を控えに残して main に戻れます。その後「作業開始」で新しい Issue 番号を入れ、控えから必要な内容を写してください。分からなければチームのリーダーに相談してください。 | マージ済みで GitHub から消えたブランチで、続きの作業をしようとした(正しく動いている) | 画面のとおり「やり直し(main に戻る)」→「作業開始」(新しい番号)→ 控え(`local/backup/`)から必要な内容を写す。**マージしていないのにこれが出る**ときは、GitHub の PR 一覧で本当にマージ済みか確かめる | `開始時` のブランチ名。`$ git show-ref ...` が失敗している(= `origin/〈ブランチ名〉` が無い) |
| 【die】GitHub への送信に失敗しました。手元の記録は残っています。 | ネットワークの不調、リポジトリへの権限がない(招待が未承諾)、GitHub のログインが切れている | 招待の承諾とログイン状態を確かめ、ネットワークを確かめて、もう一度実行する。手元の記録は残っているので、やり直して大丈夫 | 直前の `$ git push ...` の `[stderr]`(`Permission denied`、`Could not resolve host`、`Authentication failed` など) |
| 【die】GitHub への送信に失敗しました。 | 上と同じ(「作業開始」で新しいブランチを GitHub に送るとき) | 上と同じ | `$ git push -q -u origin ...` の `[stderr]` |
| 【die】GitHub に接続できませんでした。ネットワークを確認してください。 | ネットワークが切れている、学校の回線やVPNの制限、GitHub のログインが切れている | ネットワークを確かめる。ブラウザで GitHub が開くか確かめる。ログイン画面が出たらログインして、もう一度実行する | `$ git fetch ...` の `[stderr]` |
| 【die】同じブランチを他の人が変更していて、あなたの変更と衝突しました。取り込みは取り消したので、手元は元のままです。 | 同じブランチを 2 人が同じ箇所で変えた | 2 人で相談し、同じブランチで同時に作業しないようにする。衝突の解消には Git の知識が要るので、分からなければ作成者に相談する(手元は元のままで、何も壊れていない) | `$ git merge ...` の `[stdout]` にある `CONFLICT (content): Merge conflict in ...`(衝突したファイル名) |
| 【die】記録に失敗しました。 | 記録(commit)ができなかった。Git の設定の不備や、ディスクの空き不足など | ログの `[stderr]` に出ている文章を読む。ディスクの空きやファイルが他のソフトで開かれていないかを確かめて、もう一度実行する | `$ git commit ...` の `[stderr]` |
| 【die】手元の main を最新にできませんでした。 | 手元の main に GitHub の main と食い違う記録がある、または main が別の場所で使われている | `[stderr]` を読む。分からなければ作成者に相談する | `$ git fetch -q origin main:main` の `[stderr]` |
| 【die】ブランチを最新にできませんでした。 | 手元のブランチと GitHub のブランチが食い違っている(「作業開始」「ブランチ切り替え」のとき) | `[stderr]` を読む。同じブランチを別の PC や別の人が変えていないか確かめる。分からなければ作成者に相談する | `$ git pull -q --ff-only` の `[stderr]` |
| 【die】main の変更とあなたの変更が衝突しました。取り込みは取り消したので、手元は元のままです。 | main に入った他の人の変更と、自分の変更が同じ箇所を変えている | 衝突の解消には Git の知識が要る。作成者に相談する(手元は元のままで、何も壊れていない) | `$ git merge ... origin/main` の `[stdout]` の `CONFLICT ...` |
| 【die】ブランチの退避に失敗しました。 | マージ済みのブランチの名前を `merged/...` に変えられなかった | `[stderr]` を読んで作成者に相談する | `$ git branch -m ...` の `[stderr]` |
| 【die】ブランチを作れませんでした。 | 新しいブランチを作れなかった。同じ名前のブランチがすでにある、など | `[stderr]` を読む。`already exists` と出ていれば、名前を変えてもう一度実行する。分からなければ作成者に相談する | `$ git switch -q -c ...` の `[stderr]` |
| 【die】このブランチ(〈ブランチ名〉)は「作業開始」で作ったものではないため提出できません。 | `feature/番号` の形ではないブランチ(自分で作ったブランチなど)で「提出」を選んだ | 「作業開始」で作ったブランチに切り替えてから「提出」を実行する | `開始時` の `ブランチ:` |
| 【die】控えのフォルダを作れませんでした。 | 「やり直し」の控え(`local/backup/`)を作れない。ディスクの空き不足や権限など | ディスクの空きを確かめて、もう一度実行する。何も変わっていない | `結果: die` の前後(コマンドは `mkdir`。ログには Git のコマンドは出ない) |
| 【die】控えを取れませんでした(〈ファイル名〉)。何も変えていません。 | 変更中のファイルのコピーに失敗した。ファイルが他のソフトで開かれているなど | そのファイルを開いているソフトを閉じて、もう一度実行する。何も変えていないので安全 | 画面の文章に出ているファイル名。`---- 終了時 ----` の `git status` が `開始時` と同じ |
| 【die】元に戻せませんでした。控えは 〈控えのフォルダ〉 にあります。 | 控えは取れたが、元に戻す操作(`git reset` / `git clean`)が失敗した。ファイルが他のソフトで開かれているなど | 画面に出た控えのフォルダは消さない。開いているソフトを全部閉じて、もう一度「やり直し」を実行する。それでも出るときは作成者に相談する | `$ git reset -q --hard` または `$ git clean -q -fd` の `[stderr]` |

上の表にないメッセージが出たときも、まず `結果:` の行と、`[終了コード]` が 0 以外の `$ git ...` を見てください。Git が出したエラーの文章がそこにあります。

## 3. テンプレートの更新を取り込む

作成者がテンプレートを直したとき、各チームが自分で取り込みます(自動では反映されません)。テンプレートから作ったリポジトリは、作った時点でテンプレートとのつながりが切れているためです。

1. 作成者から Teams で知らせが来たら、テンプレートの `docs/git/CHANGELOG.md` を見る。何が直ったか、取り込むべきか、手作業が必要かが書いてある
2. 「作業開始」を実行して、更新用の Issue 番号を入れる(新しく Issue を作って、その番号でよい)
3. 次の 2 行を VS Code のターミナルに貼って実行する

   ```
   git fetch https://github.com/aozora232u/git-simple-template.git main
   git checkout FETCH_HEAD -- .vscode/tasks.json scripts tests docs/git local/.gitkeep
   ```

4. `PR.md` に「テンプレート vX.Y.Z の取り込み」のように書いてから「提出」を実行し、PR を作ってマージする(`PR.md` が未記入だと「提出」は止まる)

この方法は、**テンプレートのもの**のファイルを上書きします。アプリのテストは `tests/` 以外のフォルダに置いてください(`tests/` はこの仕組みのテスト用で、更新で上書きされます)。上書きされるのは `.vscode/tasks.json`、`scripts/`、`tests/`、`docs/git/`、`local/.gitkeep` です。`README.md`、`PR.md`、`.gitignore`、`.gitattributes` はチームのものなので、触りません。

注意: この方法では、テンプレート側で消されたファイルは、チーム側では消えません。このため、テンプレート側ではテンプレートのもののファイルを消したり名前を変えたりするのを避けています。やむを得ないときは、CHANGELOG にその版で必要な手作業が書いてあります。

## 4. 作成者に相談する

2 章で解決しないときは、次の順で相談してください。

1. **ログファイルを Teams で送る。** メンバーから預かった `local/logs/` のログファイル(`die` のときに画面に出た場所のもの)を、Teams で作成者に送る。何をしようとして、画面に何が出たかも一言添える
2. **教室で直接声をかける。** 全員が同じ教室にいるときは、ログを開いた画面を見せるのが早い

作成者: `{{作成者の名前}}`(Teams で連絡)

作成者は各チームのメンバーではなく、自分の卒業制作も進めています。ログを送らずに「動かない」とだけ送ると、原因を追えません。まずこのガイドの 2 章を確かめてから、相談してください。

## 5. やってはいけないこと

- **テンプレートのものを編集しない。** 対象は `.vscode/tasks.json`、`scripts/`、`tests/`、`docs/git/`、`local/.gitkeep`。更新を取り込むと上書きされて、直したことが消えます。直したいことや困ったことは、作成者に伝えてください
- **アプリのテストは `tests/` 以外のフォルダに置く。** `tests/` はこの仕組みのテスト用で、更新で上書きされます
- **Settings → General の「Automatically delete head branches」を OFF にしない。** 1 章 2 のとおり、提出が main に入らないのに成功したように見えます
- **ログファイル(`local/logs/`)を GitHub に送らない。** `local/` は `.gitignore` の対象です。この設定を消さないでください
- **`.gitattributes` の `*.sh text eol=lf` の行を消さない。** 消すと、スクリプトが Windows で動かなくなることがあります
- **メンバーに、2 章の表にない Git のコマンドを打たせない。** 分からなければ、まず作成者に相談してください

## テストの実行方法

テンプレートのスクリプトには自動テストがあります。作成者が更新するときに使うもので、メンバーやリーダーは普段は動かさなくて構いません。更新を取り込んだあとに確かめたいときは、Git Bash で次を実行します。

```
bash tests/run.sh
```

くわしくは [tests/README.md](../../tests/README.md) を見てください。
