# Git の使い方(リーダー向け)

チームのリーダーがこのファイルだけを読んで、準備・日常のトラブル対応・テンプレートの更新・作成者への相談ができるように書いてあります。Git に詳しくなくても進められるように書いています。メンバー向けの使い方は [member-guide.md](member-guide.md) です。先に読んでおくと、メンバーから聞かれたときに答えやすくなります。

## 1. 準備

最初に 1 回だけ行います。

1. **テンプレートからリポジトリを作る。** テンプレートの GitHub ページ(https://github.com/aozora232u/git-simple-template)を開き、緑の **Use this template** →「Create a new repository」を選ぶ。Owner は自分かチームのアカウント、名前は好きなものでよい。**Private**(非公開)でよい
2. **「マージ後にブランチを自動で消す」設定を ON にする(必須)。** 作ったリポジトリの **Settings → General** を開き、少し下にある **Automatically delete head branches** にチェックを入れる(自動で保存される)
   - **理由:** テンプレートからリポジトリを作っても、この設定は引き継がれず、初期は OFF です。スクリプトは「GitHub からブランチが消えた = 提出したものがマージ済み」と判断しています。OFF のままだと、マージした後も同じブランチで「提出」を実行したときに「提出済みの PR に反映されています」と出るのに、実際は main に入りません。成功したように見えて何も届かないので、必ず ON にしてください
3. **メンバーを招待する。** **Settings → Collaborators → Add people** で、メンバーの GitHub のユーザー名かメールアドレスを入れる(メンバー全員に、招待メールの **Accept invitation** を押してもらう)
4. **`README.md` を書き換える内容を決める。** 先頭の `{{プロジェクト名}}` を自分たちのプロジェクト名にし、「## このプロジェクトについて」に説明を書く。冒頭の「Git の使い方は member-guide.md を見てください」というリンクは残す。書き換えを GitHub に届ける方法は手順 6 に書いてある
5. **必要なら `.gitignore` に使う言語の項目を足す。** 末尾の「技術構成が決まったら、言語やフレームワーク用の項目をここに追記する」のところに足す(これも手順 6 で届ける)
6. **自分の PC で 5 つのメニューが動くことを確かめる。手順 4・5 の書き換えも、ここで GitHub に届ける。** 新しいリポジトリには Issue が 1 つもないので、先に GitHub で Issue を 1 つ作る(リポジトリの **Issues → New issue**。題名は「README を書く」などでよい)。次に、リポジトリをクローンして VS Code で開き、メンバー向けガイドの手順どおりに「作業開始」(今作った Issue の番号を入れる。ブランチが新しく作られる)→ `README.md`(必要なら `.gitignore` も)を編集 → 続きの作業を試すなら「ブランチ切り替え」で自分のブランチ(一覧で「← あなたのブランチ」と付く)を選ぶ → PR.md を書いて「提出」→ 提出ページで **Create pull request** → マージ、まで一度通す。マージしたあと、GitHub 上でそのブランチが自動で消えることも確かめる(消えなければ手順 2 をやり直す)
7. **メンバーにクローン用の URL を伝える。** リポジトリのページの緑の **Code** ボタンに出る `https://github.com/...git` の URL です

## 2. よくあるエラーと直し方

### ログの見方

メンバーが「相談」するとき、`local/logs/` のログファイルを見せてもらってください。1 回の実行(メニューを 1 回選ぶごと)につき 1 ファイルできます。ファイル名は `2026-10-21_123456_start.log` のように「日付_時刻_メニュー名」です(メニュー名は `start`=作業開始、`switch`=ブランチ切り替え、`submit`=提出、`reset`=やり直し、`restore`=控えを戻す)。新しい 50 件だけ残り、古いものは自動で消えます。ログは各自の PC にだけあり、GitHub には送られません。

ログはメモ帳で開けます。見る場所は次の 4 つです。

- **`結果:` の行(読むなら最初にここ)。** `結果: 成功`、`結果: stop`(メンバー自身で直せる失敗)、`結果: die`(環境の失敗。チームのリーダーへ相談)、`結果: 終了コード N`(想定外の終わり方)のどれか。`stop` と `die` では、その次の行に画面に出た文章が入る
- **`$ git ...` で始まる行。** スクリプトが実行した Git のコマンドを、1 つずつ記録している。その下に、出力が `[stdout]`(普通の出力)・`[stderr]`(エラーや警告)として入り、最後に `[終了コード] 0` のように入る。**原因は、`結果: stop` / `結果: die` の行の直前にある、`[終了コード]` が 0 以外のコマンド**。その `[stderr]` に Git が実際に言ったエラーの文章が出ている。途中に 0 以外のコマンドがあっても、正常なことがある(たとえば「提出」では、PR.md を書いてあると `git diff --quiet` が毎回 1 を返す。「差がある = 書いてある」という意味で、失敗ではない)
- **`---- 開始時 ----` のブロック。** 実行を始めたときのブランチ、HEAD(いちばん新しい記録)、`git status --porcelain`(変更中のファイル)、Git のバージョン。「いま何をしていた状態から始まったか」が分かる
- **`---- 終了時 ----` のブロック。** `stop` / `die` で終わったときだけ入る、終わったときのブランチと変更中のファイル。開始時と見比べると、途中で何が変わったか(変わっていないか)が分かる

ログにはほかに、メニュー名・日時、実行中に画面へ出した文章(`画面:` で始まる行)も入っています。

### メッセージごとの原因と直し方

画面の文章がそのまま表の左の列にあります(〈 〉の部分はその場の名前や数字が入ります)。先頭の【stop】【die】は分類の印で、画面には出ません。**stop** はメンバー自身で直せるもの、**die** は環境側の失敗で、画面に「チームのリーダーに相談してください。そのとき、このログファイルを見せてください: ...」と続くものです。

| 【die】控えの変更が、今のブランチの内容と衝突しました。戻すのは取り消したので、手元は元のままです(控えも残っています)。 | 「控えを戻す」で、控えの変更と、今のブランチ(その間に他の人が変えた内容を含む)が同じ箇所を変えていた | 手元は元のままで、控えも残っている。衝突の解消には Git の知識が要る。作成者に相談する。急ぐときは、`git stash list` で控えを確かめ、`git stash show -p stash@{0}` で控えの中身を見て、必要な内容を手で写す方法もある | `$ git stash apply ...` の `[stdout]` の `CONFLICT ...`(衝突したファイル名) |
| 【die】元に戻せませんでした。 | 「控えを戻す」で衝突したあと、手元を元に戻す操作(`git reset` / `git clean`)が失敗した。ファイルが他のソフトで開かれているなど | 開いているソフトを全部閉じて、もう一度「控えを戻す」を実行する。控えは残っているので消さない。それでも出るときは作成者に相談する | `$ git reset -q --hard` または `$ git clean -q -fd` の `[stderr]` |
| 【die】変更を捨てられませんでした。 | 他の人のブランチ(閲覧用)から離れるとき、変更を捨てる操作(`git reset` / `git clean`)が失敗した。ファイルが他のソフトで開かれているなど | 開いているソフトを全部閉じて、もう一度実行する | `$ git reset -q --hard` または `$ git clean -q -fd` の `[stderr]` |
| 【die】ブランチ 〈ブランチ名〉 を開けませんでした。 | 他の人のブランチを閲覧用(`view/...`)に開く操作が失敗した | `[stderr]` を読む。分からなければ作成者に相談する | `$ git switch -q --no-track -C view/... origin/...` の `[stderr]` |
| 【die】main の変更とあなたの変更が衝突したため、提出を中止しました。取り込みは取り消したので、手元は元のままです。(PR.md を書いたあとに出たときは、続けて「PR.md も書いた内容に戻しました。」と出る) | 「提出」で最初に main の変更を取り込むとき、main に入った他の人の変更と自分の変更が同じ箇所を変えていた。GitHub に送る前に手元で見つけて止まっている | 手元は元のままで、PR.md に書いた内容も戻っている。衝突の解消には Git の知識が要る。作成者に相談する | `$ git merge ... origin/main` の `[stdout]` の `CONFLICT ...`。`$ git checkout -q origin/main -- PR.md` のあとに `PR.md も書いた内容に戻しました。` |

上の表にないメッセージが出たときも、まず `結果:` の行と、`[終了コード]` が 0 以外の `$ git ...` を見てください。Git が出したエラーの文章がそこにあります。

### 別の PC での注意(既知の制約)

「ブランチ切り替え」や「提出」は、そのブランチの**最初の記録(コミット)の作者**のメールか名前が、その PC の `git config user.email` / `user.name` と同じかで、自分のブランチかどうかを決めています。そのため次の 2 つが起きます。

- **まだ 1 回も記録のない自分のブランチを、別の PC で開くと、閲覧用(他の人のブランチ)として開く。** 「作業開始」を実行したその PC では、手元にそのブランチがあるので自分のものと扱われますが、別の PC には手元にないためです。そのブランチに 1 回でも記録(「ブランチ切り替え」などでの自動記録)が入れば、自然に解消します
- **メンバーの名前やメールが PC ごとに違うと、自分のブランチが他の人のものに見える。** 「他の人のブランチは提出できません」が出たら、`git config user.email` と `git config user.name` を、ブランチを作ったときの PC と同じにしてもらう。GitHub の Settings → Emails の noreply アドレスを使っていれば同じになります

## 3. テンプレートの更新を取り込む

作成者がテンプレートを直したとき、各チームが自分で取り込みます(自動では反映されません)。テンプレートから作ったリポジトリは、作った時点でテンプレートとのつながりが切れているためです。

1. 作成者から Teams で知らせが来たら、テンプレートの `docs/git/CHANGELOG.md` を見る。何が直ったか、取り込むべきか、手作業が必要かが書いてある
2. 「作業開始」を実行して、更新用の Issue 番号を入れる(新しく Issue を作って、その番号でよい)
3. 次の 2 行を VS Code のターミナルに貼って実行する

   ```
   git fetch https://github.com/aozora232u/git-simple-template.git main
   git checkout FETCH_HEAD -- .vscode/tasks.json scripts tests docs/git local/.gitkeep
   ```

4. `PR.md` に「テンプレート vX.Y.Z の取り込み」のように書いてから「提出」を実行し、PR を作ってマージする(`PR.md` が未記入だと「提出」は止まる)

この方法は、**テンプレートのもの**のファイルを上書きします。アプリのテストは `tests/` 以外のフォルダに置いてください(`tests/` はこの仕組みのテスト用で、更新で上書きされます)。上書きされるのは `.vscode/tasks.json`、`scripts/`、`tests/`、`docs/git/`、`local/.gitkeep` です。`README.md`、`PR.md`、`.gitignore`、`.gitattributes` はチームのものなので、触りません。

注意: この方法では、テンプレート側で消されたファイルは、チーム側では消えません。このため、テンプレート側ではテンプレートのもののファイルを消したり名前を変えたりするのを避けています。やむを得ないときは、CHANGELOG にその版で必要な手作業が書いてあります。

## 4. 作成者に相談する

2 章で解決しないときは、次の順で相談してください。

1. **ログファイルを Teams で送る。** メンバーから預かった `local/logs/` のログファイル(`die` のときに画面に出た場所のもの)を、Teams で作成者に送る。何をしようとして、画面に何が出たかも一言添える
2. **教室で直接声をかける。** 全員が同じ教室にいるときは、ログを開いた画面を見せるのが早い

作成者: 北山(Teams で連絡)

作成者は各チームのメンバーではなく、自分の卒業制作も進めています。ログを送らずに「動かない」とだけ送ると、原因を追えません。まずこのガイドの 2 章を確かめてから、相談してください。

## 5. やってはいけないこと

- **テンプレートのものを編集しない。** 対象は `.vscode/tasks.json`、`scripts/`、`tests/`、`docs/git/`、`local/.gitkeep`。更新を取り込むと上書きされて、直したことが消えます。直したいことや困ったことは、作成者に伝えてください
- **アプリのテストは `tests/` 以外のフォルダに置く。** `tests/` はこの仕組みのテスト用で、更新で上書きされます
- **Settings → General の「Automatically delete head branches」を OFF にしない。** 1 章 2 のとおり、提出が main に入らないのに成功したように見えます
- **ログファイル(`local/logs/`)を GitHub に送らない。** `local/` は `.gitignore` の対象です。この設定を消さないでください
- **`.gitattributes` の `*.sh text eol=lf` の行を消さない。** 消すと、スクリプトが Windows で動かなくなることがあります
- **メンバーに、2 章の表にない Git のコマンドを打たせない。** 分からなければ、まず作成者に相談してください

## テストの実行方法

テンプレートのスクリプトには自動テストがあります。作成者が更新するときに使うもので、メンバーやリーダーは普段は動かさなくて構いません。更新を取り込んだあとに確かめたいときは、Git Bash で次を実行します。

